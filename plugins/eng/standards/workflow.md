Standing instructions from the user for any change to code, config, or docs.

1. Understand first. Read what the request points to (ticket, thread, PR, error, docs), then the code, its history, and the repo's own guidance (`.claude/` skills, AGENTS.md, CONTRIBUTING), whose format rules beat an eng skill's defaults. Pin down current and expected behaviour, root cause, constraints, and blast radius. A reported bug needs real signal, such as an error or a log, before a fix is proposed. Use the `eng:investigate` skill.
2. Plan, then stop. Ask each question the plan raises at planning, one at a time with a recommendation, never mid-run. The plan ends with a Delivery section, and is a file when it lists writes. Check every finding, plan and report in rounds until independent passes agree, two at the least: only a blocker starts another round, and one open after round 3 becomes a question. Ask for approval once no check runs and the latest round agreed. A request to investigate, plan, or review is not permission to edit.
3. Implement when the user approves the plan or names the exact change, and log a ruling for what the plan missed, never a question or a wait. Review with `/code-review high <base>..HEAD`, `medium` on each fix diff, never --comment, --fix, or ultra, plus the security review when the diff touches a trust boundary, and fix the valid findings. After a PR opens and each push, the session reviews the commits no review has read. A request to review a PR or diff goes to /code-review. Work is ready only when every check passes and no blocker remains. Use the `eng:implement` skill.
4. Write outside this machine only when the user's latest message asks for it, or the Delivery of a plan they approved, a change they named, or their open PR's branch covers it and the work is ready. Merges, releases, tags, deploys, pushes to the default branch, and force pushes other than `eng:commit`'s explicit-lease push to another branch need the latest message, and so does a change to global config such as `~/.claude/settings.json`. Use the `eng:commit`, `eng:pr` and `eng:issue` skills.
5. Post no comment, review, or reply. Draft each as Markdown in your scratchpad, else ${TMPDIR:-/tmp}/drafts, with the command to post it, and give the path. Judge PR feedback against the code with the `eng:pr-feedback` skill.
6. Final updates, and every other reply, lead with the result, then what you found and ran, what you did not check, any risk, and one next action, leaving out empty items and anything already shown.

Where skills have no plugin prefix, `eng:<name>` is the skill named `<name>`. In a subagent, the brief beats these steps, except steps 4 and 5.
