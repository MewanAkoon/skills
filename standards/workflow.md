Standing instructions from the user for any change to code, config, or docs.

1. Understand first. Read what the request points to (ticket, thread, PR and its threads, error, docs), then the code, its git history, and the repo's own guidance for the task as files (`.claude/` skills and commands, AGENTS.md, CONTRIBUTING). That guidance's format rules beat an eng skill's defaults. Pin down current and expected behaviour, root cause, constraints, and blast radius. Use the `eng:investigate` skill.
2. Plan, then stop. Write a short plan, check it against the code, the findings, and the repo's patterns, and revise it until the check is clean. Then wait. A request to investigate or plan, or to review or validate someone else's work, is not permission to edit.
3. Implement when the user approves the plan or names the exact change. Follow the plan and the repo's patterns, prefer the clean solution to the smallest diff, test the behaviour that changed, and correct any doc the change makes false. Use the `eng:implement` skill.
4. Review before handing back. The `eng:implement` skill ends in a review loop through the built-in /code-review. A request to review a PR or a diff goes to /code-review directly. Never pass --comment, --fix, or ultra. Call work ready only when every check passes and no blocking finding remains.
5. Write outside this machine only when the user's latest message asks for it: a commit, push, PR, issue, label, merge, release, tag, publish, deploy, remote migration, or an MCP write beyond editing a doc or sheet. Commits go through the `eng:commit` skill, PRs through `eng:pr`, and issues through `eng:issue`. An earlier go-ahead does not carry forward. Finishing a merge, rebase, cherry-pick, or revert that git has paused is part of resolving it.
6. For PR feedback, judge each comment against the code before acting on it. Fix the valid ones the user asked you to address, run step 4 again, and say when it is ready to commit. Use the `eng:pr-feedback` skill. After a PR opens and each push, review the whole PR with `/code-review high <merge-base>..HEAD` (or `eng:implement`'s fallback), judge its findings the same way, fix the valid ones, and ask about what only the user can decide. Stop and report when two pushes in a row bring new valid blocking findings.
7. Never post a comment, review, or reply on GitHub, Jira, Slack, or similar. Write the draft to a Markdown file in your scratchpad directory, or in ${TMPDIR:-/tmp}/drafts without one, with the command that would post each one, and give the path.
8. Final updates say what happened, what you found, what you ran to verify it, what you did not check, any risk, and where things stand. No narration.

A named exact change or an approved plan starts at step 3. A reported bug needs real signal (the error, the log, the failing request) before a fix is proposed. The user's framing is a hypothesis until then. In a subagent, the brief takes precedence over these steps, except steps 5 and 7.
