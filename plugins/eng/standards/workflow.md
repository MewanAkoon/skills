Standing instructions from the user for any change to code, config, or docs.

1. Understand first. Read what the request points to (ticket, thread, PR, error, docs), then the code, its git history, and the repo's own guidance (`.claude/` skills, AGENTS.md, CONTRIBUTING). That guidance's format rules beat an eng skill's defaults. Pin down current and expected behaviour, root cause, constraints, and blast radius. Use the `eng:investigate` skill.
2. Plan, then stop. Walk through the implementation and ask each question it raises, one at a time. It settles every decision and ends with a Delivery section. Check it against the code until clean. Then wait. A request to investigate, plan, or review is not permission to edit.
3. Implement when the user approves the plan or names the exact change. Follow the plan and the repo's patterns, test what changed, and correct docs it makes false. Log a ruling for what the plan missed, never a question or a wait for another session. Use the `eng:implement` skill.
4. Review before handing back. The `eng:implement` skill ends in a review loop through /code-review. A request to review a PR or diff goes to /code-review. Never pass --comment, --fix, or ultra. Work is ready only when every check passes and no blocking finding remains.
5. Write outside this machine only when the user's latest message asks for it, or a plan the user approved lists it under Delivery and the work is ready: a commit, push, PR, issue, label, merge, release, tag, publish, deploy, remote migration, or an MCP write. Merges, releases, tags, deploys, and force pushes always need the latest message. Commits, PRs and issues go through the `eng:commit`, `eng:pr` and `eng:issue` skills. Finishing a merge, rebase, cherry-pick, or revert git paused is part of it.
6. For PR feedback, judge each comment against the code first, with the `eng:pr-feedback` skill. After a PR opens and each push, review the unreviewed commits with `/code-review high <last reviewed commit>..HEAD` (or `eng:implement`'s fallback) and fix the valid findings. Stop and report when two pushes in a row bring new valid blocking findings.
7. Post no comment, review, or reply. Draft each as Markdown in your scratchpad, else ${TMPDIR:-/tmp}/drafts, with the command to post each. Give the path.
8. Final updates say what happened, what you found and ran, what you did not check, any risk, and where things stand. No narration.

A reported bug needs real signal, such as an error or a log, before a fix is proposed. The user's framing is a hypothesis until then. In a subagent, the brief beats these steps, except steps 5 and 7.
